# Tooling

## CLI

統合CLIのprogram名は`altc`です。

| Command | 契約 |
| --- | --- |
| `altc check` | parse、名前解決、型・effect検査、memory access summary推論を行い、C toolchainとartifactを要求しない |
| `altc check --ffi` | frontend検査に加え、検証用C translation unitでextern宣言とheaderを照合する |
| `altc build` | FFI検証、C11生成、C compiler、linkerを実行してbinaryまたはlibraryを作る |
| `altc run` | buildしたprogramを実行し、`--`以降をprogramへ渡す |
| `altc test` | FFI検証後にtestとdoc testを発見、build、実行して結果を報告する |
| `altc doc` | 公開symbolとMarkdown doc commentからHTMLを生成する |
| `altc lsp` | stdioでLanguage Server Protocol serverを起動する |
| `altc emit-c` | C11 sourceと必要なheaderだけを保存する |
| `altc fmt` | CSTに基づくcanonical formattingを行う |

single-file commandはproject設定なしで動作しなければなりません。multi-module build設定のfile formatはimplementation-definedですが、source root、output kind、C compiler、include path、define、library、C flag、linker flagを再現可能に指定できなければなりません。

compilerの選択順位、target既定値、環境変数の扱いもimplementation-definedです。`--verbose`または同等の機能で、解決後のC compiler・linker commandと主要設定を確認可能にします。

`altc check`だけではextern contractがC headerと一致することを保証しません。`--ffi`なしの結果はfrontend検査済み、FFI未検証としてmachine-readable outputとLSPから区別できなければなりません。buildとtestからFFI検証だけを無効化するoptionは提供しません。

## Diagnostic

human-readable diagnosticは最低限、error code、severity、message、primary source span、必要なsecondary label、note、修正可能なhelpを持ちます。compiler内部pass名だけを利用者向け説明にしてはなりません。

machine-readable modeは、一diagnosticにつき次の情報を構造化して出力します。

- stable diagnostic code
- `error`、`warning`、`note`のseverity
- human-readable message
- source fileとUTF-8 byte単位のstart/end offset
- line/column表示用位置
- primary/secondary label
- related noteとhelp
- 原因がC toolchainの場合は元commandと元diagnostic

構文errorの後も可能な範囲でparseを継続し、一回の`check`で独立した複数errorを報告します。

## C toolchain

backendはC11 modeを明示し、include path、macro define、warning、optimization、debug info、library、linker argumentを既存toolchainへ渡します。外部commandの終了code、stdout、stderrを隠してはなりません。

FFI検証用translation unitもbuild本体と同じtarget、C compiler、include path、macro define、ABIへ影響するflagでcompileします。検証失敗と通常の生成C compile失敗はdiagnostic上区別します。

altc sourceと生成Cの位置対応には`#line`を使い、C compiler diagnosticとdebug infoを可能な限り`.altc`へ戻します。対応不能なC diagnosticには生成file位置も併記します。

## Formatter

formatterはCSTを入力にし、commentとdoc commentを失ってはなりません。同じsourceを二度formatした結果は同一でなければなりません。canonical indentationは2 spacesとし、tabをindentationとして出力しません。

syntax errorを含むfileは、意味を変えない範囲だけformatするか、変更せずdiagnosticを返します。tokenを推測で削除してはなりません。

## LSP

LSPはcompilerと同じCST、source span、symbol ID、型、effect、memory access summary、doc情報を使い、少なくとも次を提供します。

- syntax・名前・型・effect diagnostic
- completion
- hoverによる型、signature、effect、memory access summary、doc表示
- definition jumpとreference検索
- document/workspace symbol
- scope-aware rename
- signature help
- inferred type、effect、memory access categoryと根拠spanの問い合わせ
- extern宣言のFFI検証済み・未検証・期限切れ状態

編集途中の不完全なsourceでも、回復できた領域の情報を返します。incremental cacheの粒度は非規範的ですが、古い意味情報を現在のsource位置へ誤って返してはなりません。FFI検証cacheにはheader content、target、C compiler identity、include path、macro define、ABI optionを含めます。

memory access summaryの表示では、function自身に直接含まれるcategoryとcall経由で推移的に含まれるcategoryを区別できなければなりません。call経由のcategoryには、少なくとも最初のcall siteと到達先functionを示します。表示には対象source revisionを対応付け、signatureやABI contractではないことを区別します。summaryを使うlintは既定でcore language errorにしてはならず、有効化とseverity policyを利用者が選べなければなりません。

## Test

`altc test`はtest blockごとに識別可能な結果を出し、altc compile error、C compile/link error、test failure、process crashを区別します。testの実行順に依存するprogramは保証されません。test runnerが追加するruntimeはtest artifactだけに含めます。

## Documentation

`altc doc`は`///`のMarkdownを公開module、type、field、variant、function、method、traitへ関連付け、HTMLにstableなsymbol anchorを生成します。functionとmethodには宣言されたeffectと推論したmemory access summaryを別項目として表示し、source定義へのpathとspanを保持します。

doc comment内の`altc` code fenceはdoc testです。`ignore`と明示されたblockを除き、`altc test`がcompileし、期待outputが指定されていれば比較します。通常のMarkdown fileにある`docs/examples/`の推定Cはdoc testやgolden outputとして扱いません。

## Commentと生成C

外部へ保存する各C sourceとheaderの先頭行には、`/* Generated by altc. Do not edit. */`を一度だけ出力します。生成元の表示を目的として、個々の内部identifierへ`altc`接頭辞を付けてはなりません。衝突回避に使う実際のmanglingはimplementation-definedです。

通常commentは対応する宣言、statement、expression nodeへ決定的にattachし、生成Cの近くへ残します。元sourceの正確な空白とcomment columnは保証しません。doc commentは生成documentationの正本であり、生成Cへ残すかどうかは非規範的です。
